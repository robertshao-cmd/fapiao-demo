## 一、現況:demo 裡的付款是模擬,不是真整合

實測過(`user.html` 的 `renderCheckout()`/`isOnline()`):

- **已接第三方支付**(線上):結帳頁三顆鈕(LINE Pay/信用卡/Apple Pay),點下去只是切換 UI 狀態
  (`pick(this)`),**沒有呼叫任何真的金流 SDK 或 API**。下單後直接標記 `paid:true`、生一組假發票號。
- **未接第三方支付**(到店付款):訂單先送出,付款發生在取餐/送達那一刻(現金/店內刷卡/貨到付款),
  外加一個「履約保障」機制——連續跑單會暫停到店付款資格,除非綁信用卡擔保(這段也是模擬)。
- 商家端(`merchant-app.html` 開店步驟 3「營運與支付」)讓商家二選一:接第三方支付(線上收款、
  T+1 撥款)或先用到店付款(0 串接成本);兩種都寫「基礎服務 0 抽成」。
- 核銷台的「3–6%」是**券核銷的抽成**,跟付款處理費是兩件不同的事,不要混在一起問人。

**這一段目前全部是前端狀態切換,沒有任何一行程式碼真的碰過金流。**

## 二、方法論:拆解 quickclick.cc(快一點 LINE點餐)+ DDPay 學到的

(完整拆解見對話紀錄;這裡只留下可以直接套用的三個結論)

1. **單一結帳畫面聚合多種支付方式**——現金/LINE Pay/Apple Pay/Google Pay/信用卡全部長在同一個
   畫面,後面接哪個支付軌是實作細節。**我們的結帳畫面已經是這個形狀,不用改介面,要接的是後面。**
2. **收款跟讀發票載具是同一個物理動作**,不是兩步——他們的收款裝置(商米 V3 MIX)感應收信用卡的
   同時,內建掃碼模組讀客人的發票載具號。這是核銷台未來要往哪個方向長的參考(見 HANDOFF 候選)。
3. **DDPay 是「一次申請開通,多種支付任選」的聚合層**——重點不是他們的裝置,是「商家不用一家一家
   自己申請刷卡機、串 LINE Pay」這個聚合角色本身。**這個角色由誰來扮,是下面第三節要先問清楚的事。**

## 三、先問 Melon 的策略題(比工程問題更前面,順序不能反)

**這題不問清楚,下面工程那幾條問了也白問**——問法向決定了要找誰、要接哪一層。

> 「消費事業群不爭利三原則」的精神下,我們是要:
>
> - **(A) 只當資料層**:付款這件事完全交給點到/商家自己現有的收款方式(可能是點到自己有串,
>   也可能是商家自己的 POS/現金),我們只在事後讀「這筆訂單付了多少、什麼時候付的」——
>   跟現在讀發票 rawdata 的角色一樣,不碰錢的流動本身。
> - **(B) 自己做聚合層**:像 DDPay 那樣,由我們(或找一家像 DDPay 的既有服務商)幫商家把多種
>   支付方式收斂成一個入口,我們就會直接參與金流,要面對 PCI DSS、第三方支付牌照這類合規問題。

demo 目前的介面(結帳頁自己切支付方式)其實已經**假裝**選了 (B),但沒人真的拍板過。
問 Melon 的具體問題:**這條線要不要碰金流本身,還是永遠停在「讀結果」?**

## 0803 結論:現況已經是(A),而且比原本想的更完整

- **我們完全不用蓋支付聚合層**——這件事點到已經做了,「DDPay 那種聚合角色」點到自己就是。
- 客人在點到線上點餐頁付款,**錢真的當下就走街口支付/LINE Pay 的金流軌**,不是等到店結帳才動——
  這跟原本以「點到不開發票=點到不碰錢」推論出的「現金流向實況」不完全一樣,那份文件要修正

  這句話還沒被推翻,只是現在多一個問題要確認,見下面新增的問題)。

策略題(A)vs(B)基本上已經有答案——**是(A)**,不用再問 Melon 要不要碰金流本身,
